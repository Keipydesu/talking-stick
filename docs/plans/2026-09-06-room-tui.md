# Room chat — an interactive human client for `tt`

> **Status:** converged claude + codex design. This document is the
> implementation contract.
>
> **Convergence path:** claude drafted, codex reviewed adversarially and
> returned a conditional veto on two lifecycle blockers, both of which claude
> reproduced in source and accepted. Outcomes: claude conceded the command
> name (`tt chat` primary, not `tt tui`) and the presence-refresh design (the
> draft's periodic self-poll was unsafe); codex's blockers stood unamended.
> Claude then added three gaps neither draft had listed — the harness guard,
> owner-quit cleanup, and startup backlog. Zero-dependency and inline
> rendering were agreed without dispute.
>
> **Review amendment:** implementation review selected discoverable
> `/quit --force` over a timing-sensitive double-Ctrl-C escape hatch. It first
> performs a normal release with a default handoff and exits only after that
> release succeeds. A failed exit release must leave both guardian and CLI
> session intact and return a recovery error; cleanup without a successful
> release can create an untracked, indefinitely renewed lease. Production
> event waits use the joined room's `waitForEventsMaxWaitMs` policy, while
> tests may inject a shorter wait.

## Problem

Wojtek's pushback: *"the text interaction with talking-stick has a hard
learning curve and rather unintuitive; it is hard to figure out how to send a
message to a room, join a room etc."*

The human CLI surface is ~25 commands with optional positional paths, a
boolean-flag registry, and a structured handoff payload. A person who wants to
do the two obvious things — *be in the room* and *say something to it* — must
already know `tt join`, `tt msg send room "..."`, and `tt wait`. Worse, send
and receive are different processes: `tt wait` blocks in one terminal while
`tt msg send` happens in another, so there is no single surface where "what is
happening" and "what can I do about it" are both visible.

The CLI is well-shaped for agents, which read `--json` and never forget a flag.
It is badly shaped for the human watching them.

## Goal

One command, `tt chat` (alias `tt tui`), that:

1. joins the room for the cwd (idempotent) with no arguments,
2. streams room activity as a readable chat log,
3. sends a room message when the user just types text and presses enter,
4. exposes **common room actions** through a discoverable `/` palette with
   completion and guided argument entry, and
5. teaches the CLI by echoing the equivalent `tt` command for each action.

`chat` is primary because it is the novice's word for the intent; `tui` names
the implementation and survives as an alias. `room` was rejected as
noun/action ambiguous.

**Non-goals.** Replacing agent-facing `tt wait`. Covering the full 25-command
surface — `/help` points at `tt help` for administration. Multi-room
switching, mouse support, and themes.

## Shape

### Rendering model — inline, not alternate-screen

A scrolling chat log on the normal screen buffer:

```
  ... scrollback (native, copyable) ...
  14:02  codex     -> room   pushed the parser refactor
  14:02  .         claude joined
  -- room talking-stick . 3 members . stick: codex (12m) ----------
  >
```

The log is ordinary `stdout` lines. Only the bottom two lines — status bar and
input — are cursor-managed, redrawn on state change and on `SIGWINCH`.

**Rejected:** a full-screen alternate-buffer TUI with panes. It costs native
scrollback, terminal copy/paste, and reflow-on-resize, and needs a layout
engine to earn back what the shell already provides.

### Dependencies — none new

`node:readline` plus ANSI escapes. This package has two runtime dependencies
and installs globally; `ink` would pull React and a large transitive tree to
manage a two-line region. Guided handoff is two sequential readline prompts
and does not justify a UI framework.

### Process model — in-process, no subprocess

The client imports `TalkingStickService` / `TalkingStickCommands` directly, the
way `src/cli/*` already does. It never shells out to `tt`.

#### Receive loop (agreed, replaces the draft's self-poll)

`service.waitForEvents()` does not route through `registerReceiver`
(verified: `src/service.ts:1914` vs `~1296`), so it cannot raise
`duplicate_listener` and cannot collide with an agent's `tt wait`.

One **sequential** loop, never two concurrent pollers:

1. long-poll `waitForEvents({ target_agent_id: "any" })`, capped at
   `waitForEventsMaxWaitMs` (110s),
2. render the returned events, advance the cursor from `cursor_event_seq`,
3. refresh presence with `commands.getRoomState({ room_id, agent_id,
   process_metadata })`,
4. repeat.

**Why not the draft's `target: "self", max_wait_ms: 0` poll.** It reaches
`recordReceiverPresence` (`src/service.ts:2966`), which passes
`allowCreate: true` *and*, on resurrection, appends a synthetic `join` event
with reason `"registered by self-targeted event receiver"`. A kicked user
would silently rejoin and emit a spurious join into everyone's stream.
`getRoomState` instead routes to `touchKnownMember` with `allowCreate: false`,
which refreshes an existing member and is a silent no-op for a removed one —
matching the documented house rule in `CLAUDE.md`. Non-owner presence cannot
use `heartbeat()`; that requires a `lease_id`.

The 110s cycle keeps the refresh comfortably inside `heartbeatIntervalMs`
(5m) and `presenceTtlMs` (4h).

**Exit conditions.** On a self-targeted kick or leave, on room close, or on
`unknown_member` from a write, the client stops and explains. It re-joins only
on an explicit user action, never automatically.

#### Turn-session lifecycle (blocker — do not shortcut)

Direct `TalkingStickCommands` turn calls are **not** equivalent to the CLI.
`handleTakeCommand` (`src/cli/turn-commands.ts:428`) spawns a guardian and
persists `lease_id` / turn / `guardian_pid` via `upsertCliSession`;
`release`/`pass`/`assign` (`:473`, `:510`, `:551`) read that session,
`clearCliSessionLease`, then terminate the guardian. A client calling
`takeoverStick()` directly would hold an **unguarded lease that silently
expires**, and a later `tt release` from any terminal would find no session to
clear.

**Resolution:** extract a non-printing turn-session controller shared by the
existing CLI handlers and the chat client. Extraction, not reimplementation —
it also gives those handlers test coverage they currently lack. Land it as its
own commit before the chat client so a regression is bisectable.

**Write authority.** The client never calls `waitForTurn` implicitly. `/take`,
`/release`, `/pass`, and `/assign` are explicit user actions.

### Entry guards

- **Harness guard.** `tt chat` under a detected harness identity must refuse
  and point at `tt wait`. Identity already distinguishes harness from human
  (`src/identity.ts`; `tt whoami --explain`). Without this, an agent that
  reads the README can launch an interactive client and hang forever holding a
  room slot.
- **Non-TTY.** Refuse with a pointer to `tt events --follow`.

Both guards live in the CLI entry (`src/cli/chat-command.ts`), **not** in
`app.ts`. `app.ts` takes an injected terminal adapter — input stream, output
stream, columns, `isTTY`, raw-mode toggle — so the headless test constructs it
over `PassThrough` with `isTTY: false` and no guard fires. The guard is real
in production and absent in tests, with no "test mode" flag.

## Action palette

Plain text with no leading `/` sends `tt msg send room <text>`. This is the
default path and requires no knowledge at all. Trim only to detect an empty
line; preserve intentional internal spacing and body content.

| Slash | Maps to |
| --- | --- |
| `/help [cmd]` | built-in; points at `tt help` for the full surface |
| `/msg <agent> <text>`, `/dm` | `tt msg send <agent> ...` |
| `/who`, `/members` | member view |
| `/state`, `/health` | `tt state` / `tt health` |
| `/history [n]` | `tt events --limit n --target any` |
| `/note <text>`, `/notes` | `tt notes add` / `tt notes list` |
| `/take [reason]` | `tt take --reason` |
| `/release`, `/pass` | guided handoff form |
| `/assign <agent>` | guided handoff form |
| `/kick <agent> [reason]` | `tt kick` |
| `/instructions` | `tt instructions show` |
| `/rooms` | `tt list` |
| `/quit` | detach, remain a member |
| `/leave` | remove membership |

Three rules keep this from becoming another thing to memorize:

1. **No-arg invocation never errors.** `/assign` with no agent opens an inline
   numbered picker of live members. `/release` opens a two-field guided prompt
   (`status`, `next_action`) instead of demanding remembered flag names. This
   is the highest-value item in the plan: the structured handoff is the
   hardest part of `tt` to use from memory.
2. **Tab completes commands and arguments.** Agent-name completion for `/msg`,
   `/dm`, `/assign`, and `/kick` is drawn from live membership.
3. **Every action echoes its CLI equivalent** as a dim `-> tt ...` line, so the
   client teaches the CLI it wraps rather than hiding it. Echoed lines must be
   shell-quoted so a copied line actually runs.

The status bar carries a contextual nudge driven by room state: `your turn —
/release when done`, `stick free — /take`, `takeover available`.

### Startup backlog

Seed the log with the last ~50 events via `getRoomEventsView` (target any),
render them dimmed as history, then tail from the returned cursor. One code
path, so there is no gap and no double-render between backlog and live tail.
Opening to a blank screen in an active room is the same disorientation this
feature exists to fix.

Call `getRoomEventsView` with `include_all: false` and without `limit` or
`after_event_seq`; supplying either would select the full-history query from
the beginning rather than the bounded recent view. Show its hidden older-event
count and initialize the tail cursor to the maximum of the join cursor and the
last rendered event. Room-state presence refreshes never advance that cursor.

### Rendering invariant

The client never renders a local copy of anything that will arrive as an
event. The event stream is the single source of truth, so no optimistic echo
and no `event_seq` dedupe is needed — correct by construction. Teaching lines
are local-only and exempt, since they are not messages.

### Quit while holding the stick

Plain `/quit` while owner refuses and points at `/release` or `/pass`.
`/quit --force` is the explicit escape hatch: it submits a default handoff
through the normal release controller and detaches only after success. EOF or
process termination follows the same release-before-exit rule. If release
fails, exit non-zero with a recovery path while preserving the guardian and
CLI session unchanged. Never kill the guardian or clear local lease state as
fallback cleanup; those records are the operator's recovery handle.

## Test strategy

Existing vitest + `TALKING_STICK_DATA_DIR` isolation pattern.

- `tests/tui-parse.test.ts` — input line -> action: plain-text default,
  quoting, unknown commands, ambiguous prefixes, whitespace preservation.
- `tests/tui-model.test.ts` — reducer over synthetic `RoomEvent` sequences:
  ownership transitions, join/leave, message rendering, cursor monotonicity.
- `tests/tui-render.test.ts` — status bar and log formatting; TTY vs non-TTY;
  narrow-width truncation; shell quoting of teaching lines.
- `tests/tui-app.test.ts` — headless integration over in-memory
  stdin/stdout duplexes against a temp data dir: a typed line lands as a
  `message` event; `/take` moves ownership *and* persists a guarded session;
  `/quit` while owner refuses; kick of self stops the loop; `/quit` tears down
  the poll loop and exits 0; a failed exit release preserves the still-live
  guardian and session rather than orphaning ownership.
- Turn-session controller extraction ships with tests covering the existing
  CLI handlers' guardian and session behavior, so the refactor is pinned
  before the client depends on it.

## Risks

- **Terminal handling is the bug farm**, not the protocol. Raw-mode restore
  must be centralized in the terminal adapter, in a `finally` plus
  `SIGINT`/`SIGTERM` handlers, or a crash leaves the user's terminal without
  echo.
- **Redraw races** between async log writes and the managed bottom region.
  Mitigation: one serialized write path — a single `redraw()` clears the
  managed region, flushes pending log lines, then repaints bar and input.
  Nothing in the poll loop calls `console.log` directly.
- **`better-sqlite3` is synchronous.** Poll-loop sleeps yield, but a large
  `/history` query blocks input. Cap query limits.
